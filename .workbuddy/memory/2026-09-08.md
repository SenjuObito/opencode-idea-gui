## 排查：上传附件没有传到 opencode server

**结论：opencode 的 FilePartInput 字段对不上，请求被服务端 400 拒绝。**

- opencode 服务端 schema（`packages/schema/src/v1/session.ts:413`）：
  `FilePartInput = { id?, type:"file", mime:string, filename?, url:string, source? }`
- idea 插件实际发送（`ai-bridge/services/opencode/opencode-daemon-service.js:629`）：
  `{ type:'file', path, mediaType:'image/png' }` —— 缺 `mime`/`url`，多出无效字段。
- 实测（本地 opencode serve v1.18.26，`POST /session/{id}/prompt_async`）：
  旧格式 → `HTTP 400 Missing key at ["parts"][1]["mime"]`；
  `{type:'file',mime,filename,url:'data:<mime>;base64,<b64>'}` 和 `url: pathToFileURL(p).href`
  均返回 204 并正确落库、内容可读。
- 次要问题：`ai-bridge/utils/cli-image-input.js:51` `resolveImageMimeType` 非 `image/`
  直接返回 null → `:169 continue`，非图片附件在进 server 前就被静默丢弃。
- 展示层：`SessionContextService.java:346 isImageAttachment` 只渲染图片，非图片只留
  `[Uploaded Attachments: x]` 占位文本，造成"已上传"的错觉。
- **opencode-vscode-plugin 有同样的 bug**（`ai-bridge/.../opencode-daemon-service.js:661`
  同款写法），不能作为正确参考；ground truth 是 opencode 源码 schema。

## 修复（已实施，idea + vscode 两个仓库同步）

`ai-bridge/utils/cli-image-input.js`
- 新增 `buildFileParts(attachments, {maxBytes})` → `{ parts, errors }`，产出合规的
  `FilePartInput`：`{ type:'file', mime, filename, url }`。
  - 有 `data` → `url: data:<mime>;base64,<b64>`（内联，远程 server 也成立，且不再写临时文件，
    因此消除了 `finally` 里删临时文件的竞态）。

  - 新增 `resolveAttachmentMimeType`（任意 mime，非图片不再丢弃）+ 扩展名嗅探兜底
    （源码文件映射到 text/plain，opencode 会把 text/plain 的 data URL 内联成可读文本）。
  - `MAX_ATTACHMENT_BYTES = 4MB`；超限/空数据一律进 `errors`，不再静默丢弃。
- 保留旧的 `materializeImageAttachments` 等导出（其他引擎可能引用），但 opencode 路径已不再使用。

新增 `ai-bridge/utils/file-parts.test.js`（两边各一份，10 个用例全绿）。
