# 四类场景分治方案（修正版：发送侧不动，核心修历史恢复）

## 需求边界（按你的确认）

| 场景 | 发送给模型 | 发送后气泡 | 历史恢复显示 |
|---|---|---|---|
| A. 上传图片 | file part（data:，现状不变） | 图片预览（现状不变） | **修复：图片预览**（现状丢失） |
| B. 上传非图片文件 | file part（data:，现状不变） | 文件 chip（现状不变） | **修复：文件 chip**（现状丢失） |
| C. 输入框用户主动 @ 引用 | 现状不变（文本 + ## Referenced Files 段） | 按输入原样（合理，不动） | 正文保留 @token（合理），剥离注入段 |
| D. IDE 上下文文件（ContextBar 开关） | 现状不变（## IDE Context 段落追加） | **已满足**：气泡用纯输入文本，不含追加段 | **修复：完全不显示** |

## 流程视角：改什么

**发送流程：不动。** 四类场景的发送形态全部保持现状——上传附件已是 file part（实测落库通过）、@ 引用与 IDE 上下文段落注入继续生效（模型都能收到）。webview 乐观气泡与 Java 回推气泡本来就基于纯输入文本，不含追加段，已满足 D 的"发送后不显示"。

**历史恢复流程：重写转换（唯一核心改动）。** 现状是"把落库 text part 全部拼接显示、忽略 file part"，改为三条还原规则：

```
opencode 落库 parts                    还原规则
────────────────────────────────────────────────────────────
text (synthetic=false)  用户正文+注入段 → ① 剥离注入段（按标题锚定：
                                          ## IDE Context / ## User's Current IDE Context
                                          ## Referenced Files / ## Active Terminal Session
                                          ## Workspace Context / ## Project Modules
                                          ## Agent Role and Instructions
                                          从标题删到下一个 ## 或文末）
                                          ② 用户主动 @token 保留显示
text (synthetic=true)   服务端Read展开  → ③ 丢弃（模型当时读过，用户不需要看）
file (mime=image/*)     图片附件        → ④ 图片预览块
file (其他)             上传文件        → ⑤ 文件 chip 块
────────────────────────────────────────────────────────────
输出 = [chips/图片在前] + [清洗后正文]，四处显示形态统一
```

规则 ① 隐藏 IDE 上下文文件（D）；规则 ③⑤④ 恢复上传文件/图片的 chip（A/B）；规则 ② 保留用户主动 @（C，"合理"）。

**历史列表标题（兜底）**：标题取首条用户消息文本。恢复链路的文本已被规则①②洗过，新写入的标题自然干净；**旧缓存里已写入的脏标题**在展示层用同一剥离规则清洗兜底。

## 改动点清单

1. **`OpenCodeMessageConverter.buildUserMessage`（核心重写）**：按上述五条规则转换 user message parts；输出 blocks = chips+图片在前、清洗后正文在后。
2. **新增 Java 工具 `UserTextSanitizer`**：注入段剥离（标题清单 + 幂等正则）。`MessageParser` 用户消息分支共用（undo/redo 回放、quick fix 等入口兜底）。
3. **webview `HistoryListItem`**：旧缓存脏 title 展示时轻量清洗（与 Java 同规则）。
4. **无需改动**：webview 发送/乐观气泡（useMessageSender、useMessageProcessing 的 sentAttachmentsRef 保留——历史消息自带 chip 后其守卫 `!blocks.some(attachment)` 自然跳过）、Java 发送链路（SessionHandler/SessionSendService/SessionContextService）、ai-bridge 全部。

## 风险

- 段落剥离靠插件自产标题锚定：用户正文恰含同标题的 `## 段`会被误剥（概率极低，接受）
- 旧会话上传文件落库里就是 data: file part → chip 恢复生效；更早"纯文本时代"的会话降级为现状显示
- ai-bridge 零改动 → 无需双仓库同步；改完源码重新 Gradle build（sandbox 副本）
